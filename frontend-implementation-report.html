01 Executive Summary

The existing DeskNu ticketing frontend (web/) was extended into a full multi-tenant SaaS product surface: tenant-aware authentication, self-service registration and pricing, an onboarding wizard, API credentials and webhooks management, checkout/billing, and a Platform Admin console for tenant and membership-plan management. Every screen is wired to the real Laravel API — nothing in this build reads from mock data or a hardcoded fixture. Where the Laravel API didn't yet support something the Stitch designs depicted, the gap was either closed with a small, real, well-scoped backend addition (documented per phase below) or the screen was built honestly without the unsupported piece, with that omission called out rather than faked.

02 What Was Built, By Phase

Phase 1 — Foundation Done

Tenant-aware auth · Platform Admin vs. tenant-workspace route split

Login/forgot-password/reset-password all accept an optional organization slug (collapsed "Signing in to a specific organization?" field), used only to disambiguate when the same email exists under more than one tenant. A new isPlatformAdmin flag on the auth context (derived from the Platform Admin role, the only correct signal — UserResource never serializes a tenant id) drives a full route-tree split: RequireTenantUser/RequirePlatformAdmin guards redirect — never error — a user into the correct half of the app, with a new minimal PlatformShell (header + small nav) for the admin side.

Also fixed along the way: the dev database had never had the 12 multi-tenant migrations applied, a real FK/index-ordering bug in one of them, and a genuine application bug where three controllers built their roles/permissions response after the tenant context had already been cleared.

Phase 2 — API Credentials Done

/integrations/api-credentials

Full CRUD against the real ApiCredentialController: grouped scope selection, one-time secret reveal (never re-fetchable, held only in local component state), rotate, and revoke behind a type-to-confirm safeguard. The design's IP-allowlist step and production/sandbox toggle were dropped — no backing column exists for either.

Phase 2B — Webhooks Done

/integrations/webhooks

Full CRUD, event subscription (8 real event types), one-time signing-secret reveal, rotate, test-send, and a genuinely server-paginated delivery log. The secret-reveal UI from Phase 2 was generalized into a shared components/security/SecretReveal.tsx rather than duplicated. No dedicated Stitch screen exists for this surface — extrapolated from the same design system.

Phase 3A — Registration + Pricing Done

/register · /pricing

Self-service tenant registration (org name, live slug-availability check, password strength meter) against POST /tenants/register, and a pricing page driven entirely by real MembershipPlan rows (a small new public GET /membership-plans endpoint was added for this — the only backend change in this phase). The design's per-agent pricing toggle and data-residency region picker were dropped — the real plan model has one flat price per plan and no residency field.

Phase 3B — Onboarding Wizard Done

/onboarding

A 5-step wizard (Departments → Team → Ticket Numbers → API Integration → Complete) built from real endpoints, including a new, small TicketNumberSetting endpoint so the ticket-number-format step configures something real. The design's 6-step version included an "Organization Profile" step with no backing tenant-self-service endpoint — dropped rather than faked.

Team invites never transmit a plaintext password: when an admin omits one, the backend generates and hashes a random password server-side and immediately sends the same real password-reset email flow already used elsewhere, so the new teammate sets their own password before ever signing in.

Phase 3C — Checkout + Billing Done

/billing · /billing/checkout

A new, small, real SubscriptionController (view/change-plan/cancel) was added, reusing the existing PlanLimitService for live per-feature usage bars — no duplicated counting logic. Plan changes and cancellation are completely real; only payment collection is out of scope (confirmed true for every tenant on every plan, not just new ones). The payment UI is an obviously-fake, read-only, pre-filled card with a persistent "Demo mode" banner — never an editable field that could be mistaken for a real capture form.

Phase 4 — Platform Admin Console Done

/platform/dashboard · /platform/tenants · /platform/membership-plans

Tenant list/filter/search, tenant detail with inline edit + suspend/activate, and membership-plan list/create/edit — the first phase built entirely against an already-complete backend (Platform/TenantController and Platform/MembershipPlanController), with no backend changes needed. A dashboard shows real, cheaply-computed tenant counts by status and plan counts rather than fabricated metrics (no MRR, no churn — nothing backs those). No tenant or plan delete exists in the API, so none exists in this UI; plans are archived via their real is_active flag instead.

03 Core Principles Followed

  • Every screen reads from and writes to the real Laravel API — no hardcoded or mock data anywhere in the shipped build.
  • Where design and API disagreed, the API's actual contract won every time — confirmed against controller/policy/resource/model source, never guessed.
  • Backend additions were kept small, real, and narrowly scoped to unblock a specific screen (public plans endpoint, ticket-number-settings endpoint, subscription endpoint) — never a shortcut to fake a response shape.
  • Existing components and patterns were reused or generalized (e.g. SecretReveal, ConfirmDialog's type-to-confirm, DataTable/Pagination, the Raw/mapped type-pair convention) rather than rebuilt per screen.
  • Tenant isolation was never compromised — every tenant-scoped request still goes through the existing TenantContext/BelongsToTenant machinery; the Platform Admin surface is a separate, role-gated branch of the route tree that cannot see into a specific tenant's workspace.

04 Security-Sensitive Decisions

DecisionReasoning
One-time secret reveal (API credentials, webhook signing secrets)Secret is held only in local component state from the create/rotate response, never written to any list/cache, cleared on unmount. The API itself never re-exposes it after the initial response.
Type-to-confirm on irreversible actionsRevoking an API credential requires typing its key; cancelling a subscription requires typing the plan slug. Extended ConfirmDialog with an optional confirmText prop rather than building a one-off dialog.
No plaintext passwords ever transmittedTeam invites and admin-created users default to "email a sign-in link" — the backend generates and hashes a random password server-side and sends a real password-reset email, reusing existing infrastructure instead of a new forced-reset flag.
Demo payment card is read-only, not a fake capture formAn editable card-number field that silently discards input trains people to type real card numbers into a form that does nothing with them. The demo card is fixed, labeled "DEMO", with a persistent banner on both the Billing and Checkout pages.
Route guards redirect, never 403-pageRequireTenantUser/RequirePlatformAdmin send a user to the correct half of the app instead of showing an error — the real authorization boundary is still the API's own platform.admin middleware and tenant-scoped policies; the frontend guard is UX only.

06 Known Gaps — Not Built, and Why

Each of these was confirmed absent by reading the actual backend source, not assumed. None are silently missing — all are reflected here and, where relevant, in the UI itself (e.g. an honest empty state instead of a broken control).

API Usage analytics (Phase 2C) No backend

No endpoint exists anywhere for per-credential or per-tenant API request metering. The design's usage/quota dashboard has nothing to read from.

Platform-level audit log viewer No backend

The existing GET /audit-logs is tenant-scoped and permission-gated — unreachable by a Platform Admin (no tenant context). Worse, AuditLog uses the tenant-scoping trait, so platform-admin-authored rows get tenant_id = NULL and wouldn't appear even if the endpoint were reachable.

Platform Admin changing a tenant's plan No backend

A tenant's subscription is only mutable by the tenant itself via its own /subscription endpoint. The tenant detail page in the Platform console shows the current plan read-only with an explanatory note, rather than a control with nothing behind it.

Tenant or membership-plan deletion No backend

Only suspend/activate exist for tenants (reversible); only is_active toggling exists for plans. No delete UI was built for either, matching the API exactly.

Real payment processing Explicitly out of scope

Confirmed true for every tenant on every plan today, not just ones created during this work — billing integration was never built anywhere in this system. Represented visually (demo card, invoices empty state) but never functionally real.

No automated frontend test suite Pre-existing gap

No unit/integration/E2E test tooling existed in web/ before or after this work. Every phase was instead verified with npm run build + npm run lint (both clean) and live Playwright scripts driving a real browser against the real Docker backend — see §8.

07 Bugs Found and Fixed During Verification

Live verification (not mocked) surfaced a handful of genuine application bugs, all fixed in this same body of work:

Role/permissions missing after login, me, and registration Fixed

AuthController::login(), AuthController::me(), and TenantController::register() all serialized the user's roles/permissions after the request's tenant context had already been cleared, so the team-scoped role lookup matched nothing. Fixed by setting the tenant context before loading roles in all three.

Migration index/FK ordering Fixed

A tenant-backfill migration dropped an index MySQL's InnoDB still needed for a foreign key, and wasn't safe to re-run. Reordered and made idempotent.

Docker Compose silently defaulting to SQLite Fixed

app/queue/scheduler services only loaded .env via env_file, which defaults to SQLite for host-side dev — nothing overrode it for the Docker path, so the containers were reading a different database than every manual check against. Fixed with explicit environment: DB/Redis/Mail overrides.

Subscription cancelled_at not cleared on plan change Fixed

Self-caught in the new SubscriptionController::update() — switching plans after a cancellation left the old cancelled_at timestamp in place. Added to the update payload.

Platform tenant detail page blanking its Subscription panel after any edit Fixed

Found during Phase 4 live verification: TenantController::update()/suspend()/activate() all return a TenantResource without eager-loading subscription or the users/customers/tickets counts the way show() does. The frontend was trusting each mutation's own response to replace the whole tenant object, silently wiping the Subscription card and stat row after every save/suspend/activate. Fixed by refetching the full resource via GET after each mutation instead.

08 How This Was Tested

Every phase was verified with npm run build and npm run lint (both clean throughout — the few lint warnings present are a pre-existing codebase-wide pattern, not something this work introduced), plus live browser verification via Playwright driving the real compiled app against the real Docker backend (MySQL, Redis, Mailpit) — not network-mocked, except briefly early on while a dev-server/database misconfiguration (see §7) was being diagnosed and fixed.

Representative live checks performed per phase: real login/registration round-trips confirmed against the database directly; password-reset emails confirmed by reading them out of Mailpit, including following the real signed verification link; plan changes confirmed via a fresh GET after every mutation; a Platform Admin suspending a tenant confirmed to actually block that tenant's users from authenticating, not just flip a cosmetic status badge; Phase 4's full suite (16 checks: login landing, dashboard metrics, list/filter/search, detail edit+save, suspend/activate round-trip, plan create/edit, and a regression check that a tenant user still gets redirected out of /platform/*) passing end-to-end against live data.

What this does not cover: no automated regression suite exists to catch future breakage — see the gap noted in §6. Testing was limited to the account types exercised during these sessions (a tenant Administrator, a Platform Admin, and newly-registered/onboarded tenants); other role/permission combinations in the existing RBAC system were not separately re-verified as part of this SaaS work.
