# Ticket Workflow

## Lifecycle at a glance

```
Customer creates ticket
        │
        ▼
Evaluate routing rules  ──▶  sets department / priority / escalate flag
        │
        ▼
Department resolved?  ──yes──▶  Auto-assign agent (workload-based)
        │
        ▼
Calculate SLA (first-response + resolution due dates)
        │
        ▼
Ticket returned to caller, already in its final state
        │
        ▼ (after DB commit)
Notification queued to the customer (and the assignee, if one was set)
```

Everything above the "after DB commit" line happens **synchronously**,
inside `CreateTicketAction::execute()` — a single call to
`POST /api/v1/tickets` returns a ticket that's already routed, assigned,
and has an SLA. Only notification *delivery* is deferred to the queue
(see `docs/notifications.md`), which is the one step allowed to be slow or
to retry without blocking the API response (section 16's "ticket creation
should not wait for email delivery").

## Ticket number vs. ticket id

Two separate identifiers, intentionally:

- **id** — a ULID (e.g. `01hxyz0123456789abcdefghj`), the database primary
  key and the value used in URLs (`/api/v1/tickets/{id}`). Chosen over an
  auto-incrementing integer specifically so ticket volume/existence can't
  be enumerated by walking integers (see `docs/architecture.md`).
- **ticket_number** — the human-facing identifier (`TKT-2026-000125`),
  generated by `GenerateTicketNumberAction` from the active
  `TicketNumberSetting`.

### Configuring the format

`TicketNumberSetting` supports a template string with these variables:

```
{prefix} {number} {year} {month} {day} {department} {department_code}
```

e.g. `{prefix}-{year}-{number}` → `TKT-2026-000125`, or
`{department_code}-{year}-{number}` → `BILL-2026-000042`.

`number_length` pads the sequence with leading zeros; `reset_period`
(`never` / `yearly` / `monthly` / `daily`) controls when the counter starts
over. **Changing these settings only affects tickets created after the
change** — a new `TicketNumberSetting` row is inserted rather than the
active one mutated, so historical ticket numbers are never altered
retroactively, and a department can have its own numbering settings
distinct from the global default.

### Concurrency safety

Two tickets created at the exact same instant can never receive the same
number. `GenerateTicketNumberAction` locks the relevant `TicketNumberSequence`
row with `SELECT ... FOR UPDATE` inside a transaction before incrementing
it — a second concurrent request blocks until the first commits. It also
retries (with a small randomized backoff) on the unique-constraint race
that can occur when two requests both try to create the *first* sequence
row for a brand-new period simultaneously.

This is exercised by a genuine concurrency test
(`tests/Feature/Ticket/TicketNumberConcurrencyTest.php`) that spawns 15 real
OS processes — not goroutine-style fake concurrency within one PHP
process — each with its own DB connection, racing to generate a number
against a shared database file, and asserts zero duplicates.

## Status workflow

Seven statuses, with a fixed, validated transition graph
(`app/Services/TicketStatusWorkflow.php`), keyed by **slug** rather than id
so renaming/recoloring a status via `PUT /api/v1/statuses/{id}` never
breaks the workflow:

```
Open ──────────┬──▶ In Progress ──┬──▶ Pending ──┬──▶ Escalated
  │            │        ▲          │      ▲       │       │
  │            │        └──────────┘      └───────┘       │
  └────────────┴──────────────────────────────────────────┘
                              │
                              ▼
                          Resolved ──▶ Closed
                              │            │
                              ▼            ▼
                          Reopened ◀───────┘
```

(`Reopened` can move to `In Progress`, `Pending`, `Escalated`, or
`Resolved` again — same as `Open`.) An attempt to make an invalid
transition — e.g. `Open` straight to `Closed` — returns `422` with
`InvalidTicketStatusTransitionException`'s message, before anything is
written.

Every transition is recorded in `ticket_status_history` (append-only) and
in the ticket's own `ticket_activities` feed. Resolving sets `resolved_at`
and checks the SLA's resolution deadline (`resolution_breached`); closing
sets `closed_at`; reopening clears both and increments `reopened_count`.

Additional, non-workflow statuses can still be created via the Statuses API
for labeling/reporting purposes, but they won't have transitions defined for
them — see the note in `docs/architecture.md` about why this was a
deliberate scope decision rather than a fully dynamic, admin-configurable
transition graph.

Thin action wrappers — `EscalateTicketAction`, `ResolveTicketAction`,
`CloseTicketAction`, `ReopenTicketAction` — each call the shared
`UpdateTicketStatusAction` with a fixed target status, and each endpoint
checks its own specific permission (`tickets.escalate`, `.resolve`, etc.)
before calling it.

## Messages and internal notes

Three message types on `ticket_messages.type`: `customer_message`,
`agent_reply`, `internal_note`. The type is **never taken from client
input as a free choice** — `TicketMessageController::store()` derives it:

- A customer's message is always `customer_message`, full stop — if a
  customer's request body includes `is_internal: true`, it is silently
  ignored, never honored.
- Staff get `agent_reply` by default, or `internal_note` only if they pass
  `is_internal: true` **and** hold `tickets.view_internal_notes`.

### How internal notes stay hidden from customers

This is enforced at three independent points, not just one field toggle:

1. **Listing** (`GET /tickets/{ticket}/messages`): the query itself excludes
   `type = internal_note` for any caller without
   `tickets.view_internal_notes` — the row is never fetched, not fetched
   and then filtered client-side.
2. **Direct access** (`GET /tickets/{ticket}/messages/{message}`): even
   knowing a specific internal note's id, a customer gets `403`.
3. **Attachments**: a file attached to an internal note
   (`TicketAttachmentPolicy`) is independently denied to anyone who can't
   view internal notes on that ticket, even if they somehow learn the
   attachment's id.

The first agent reply on a ticket also sets `first_response_at` and marks
the SLA's first-response deadline as met or breached.

## Attachments

Files are validated on upload (MIME/extension allowlist, 2 MB max, max 5
per message — `config/attachments.php`) and stored via Laravel's filesystem abstraction
(`UploadTicketAttachmentAction`) — switching `FILESYSTEM_DISK` from `local`
to `s3` (or any other configured disk) requires no application code
changes. Downloads always go through `TicketAttachmentController::download()`,
which checks `TicketAttachmentPolicy` before streaming the file — there is
no public/direct URL to a stored attachment.

## Assignment

`ticket_assignments` is **append-only**: every assignment or reassignment
inserts a new row; the row it supersedes gets `unassigned_at` stamped, never
deleted or overwritten. `AssignTicketAction` handles both the initial
automatic assignment during creation and manual (re)assignment via
`POST /tickets/{ticket}/assign` — the same endpoint also backs
`/reassign`, since the only difference is whether the ticket already had an
assignee (`assignment_type` becomes `manual` vs. `reassignment`
automatically). See `docs/routing.md` for how the initial automatic
assignee is chosen.
