# API Conventions

The full, generated endpoint-by-endpoint reference — every field, every
validation rule, every example request/response — lives in the Scribe docs
(`api/public/docs/index.html`, or run `php artisan serve` from `api/` and
open `/docs`). This page covers the conventions that apply *across* every
endpoint, which a generated reference doesn't foreground on its own.

A mobile or frontend developer should need nothing beyond this page plus
the generated reference to build against the API — not the Laravel source.

## Versioning

Every endpoint is under `/api/v1`. There is no unversioned API; breaking
changes will arrive as `/api/v2`, with `v1` kept running until clients
migrate.

## Response envelope

**Every** response — success or failure, every endpoint — has this shape:

```json
// Success
{ "success": true, "message": "Ticket created successfully.", "data": { ... } }

// Validation error (422)
{ "success": false, "message": "Validation failed.", "errors": { "email": ["..."] } }

// Unauthenticated (401)
{ "success": false, "message": "Unauthenticated." }

// Forbidden (403)
{ "success": false, "message": "You do not have permission to perform this action." }

// Not found (404)
{ "success": false, "message": "Ticket not found." }
```

A client can always safely check `data.success` first and branch on it
without needing to know the HTTP status code — though the status code is
also set correctly (200/201 success, 401/403/404/422/429/500 failure) for
clients that prefer to branch on that instead.

A paginated list response additionally includes `meta` and `links`:

```json
{
  "success": true,
  "message": "Request successful.",
  "data": [ ... ],
  "meta": { "current_page": 1, "per_page": 25, "total": 142, "last_page": 6 },
  "links": { "first": "...", "last": "...", "next": "...", "prev": null }
}
```

## Pagination, filtering, sorting

Every "list" (`index`) endpoint supports:

- `?per_page=25` — items per page, capped at 100.
- `?filter[field]=value` — exact or partial match depending on the field
  (documented per-endpoint in the generated reference as `@queryParam`).
  Example: `GET /api/v1/tickets?filter[status_id]=3&filter[department_id]=2`.
- `?sort=field` / `?sort=-field` — ascending / descending. Example:
  `GET /api/v1/tickets?sort=-created_at`.

These are implemented with `spatie/laravel-query-builder`; only the fields
explicitly listed in each controller's `allowedFilters()`/`allowedSorts()`
are accepted — an unlisted filter/sort key is silently ignored rather than
erroring, matching that package's default behavior.

## Errors

| Status | Meaning |
|---|---|
| 401 | Missing or invalid Bearer token |
| 403 | Authenticated, but not permitted to perform this action (see `docs/authorization.md`) |
| 404 | Resource doesn't exist, or (for tickets) exists but isn't visible to you — the two are indistinguishable by design, so existence can't be probed |
| 422 | Validation failed, or a domain rule was violated (e.g. an invalid ticket status transition) |
| 429 | Rate limited |
| 500 | Unexpected server error. In `APP_DEBUG=true` (local only), the response includes exception class/file/line/trace; in production it's always the generic message above |

## Authentication

See `docs/authentication.md` — Bearer token via Sanctum, obtained from
`/auth/login` or `/auth/register`.

## Ticket attachments

File uploads use `multipart/form-data`, not JSON — both
`POST /tickets/{ticket}/messages` (attachments inline with a message) and
`POST /tickets/{ticket}/attachments` (ticket-level, no message) accept
files this way. Allowed types: jpg, jpeg, png, webp, txt, pdf, docx, ppt,
pptx; 2 MB max per file, 5 files max per message (configured in
`config/attachments.php`; `ATTACHMENT_MAX_KB` overrides the size). The same
limits apply to customers, support staff and the integration API.
Downloads are authenticated — there is no public attachment URL (see
`docs/ticket-workflow.md`).

## What's documented per endpoint

The generated reference (Scribe) includes, for every endpoint: HTTP method
and URL, whether auth is required, URL/query/body parameters with type and
required/optional status, validation constraints, a realistic example for
every parameter, and at least one example success response plus the
relevant error responses. An OpenAPI 3.0 spec (`openapi.yaml`) and a
Postman collection (`collection.json`) are generated alongside the HTML —
all three live in `api/public/docs/` and are regenerated by
`php artisan scribe:generate` (see `docs/development.md`).
