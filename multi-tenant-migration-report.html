01 Executive summary

The existing Support24 Laravel API — a single-tenant customer support ticketing system with Sanctum auth, RBAC, full ticket lifecycle, routing/SLA, notifications, and Scribe documentation — has been converted into a multi-tenant SaaS platform. Every tenant-owned resource (users, customers, departments, tickets and their related records, roles, API credentials, webhooks) is isolated by an automatic, global query scope keyed to the authenticated request's resolved tenant, never trusting any client-supplied tenant identifier.

Beyond the planned feature work, this migration surfaced and fixed one critical, application-wide cross-tenant data-leak vulnerability (a Laravel middleware-ordering issue that made route-model binding run before tenant context was resolved), one severe pre-existing authorization gap in how spatie/laravel-permission's Role model was used, and a systemic pattern across roughly seventeen validation classes that predated multi-tenancy and had never been updated to respect the new tenant boundary. All are detailed in Security findings, each with a regression test that was confirmed to fail without the fix and pass with it.

02 Existing architecture audit

Before any schema change, the existing application was inventoried: Laravel 13 / PHP 8.3, Sanctum Bearer-token auth on a custom api guard, spatie/laravel-permission RBAC (5 built-in roles, resource.action permissions), a 25-table single-tenant schema, a synchronous ticket-creation pipeline (routing → auto-assignment → SLA calculation) with only notification delivery deferred to a queue, ULID keys on customer-facing tables vs bigint on reference data, knuckleswtf/scribe documentation, and 94 existing Pest tests. This existing behavior was preserved rather than rewritten — see Breaking changes for the handful of places where preservation genuinely wasn't possible.

04 New tenant architecture

App\Support\TenantContext is a per-request singleton and the single source of truth for which tenant a request operates as. It is set only by: ResolveTenantContext middleware (from the authenticated Sanctum user's own tenant_id), ResolveIntegrationTenantContext middleware (from the authenticated API credential's tenant_id), or RequirePlatformAdmin middleware (which explicitly clears it). It is never read from request input of any kind.

Every tenant-owned model uses a BelongsToTenant trait that registers a global Eloquent scope (TenantScope), transparently filtering every query by the current tenant — a controller or service never writes where('tenant_id', ...) itself. Two models (NotificationTemplate, SystemSetting) use a variant, HasTenantOverride / TenantOverlayScope, implementing a platform-default-with-tenant-override pattern instead of strict ownership.

Full detail, including the critical middleware-ordering fix, lives in docs/multi-tenancy.md (committed alongside the code).

05 API changes

122 routes now live under /api/v1, organized into:

  • Tenant-workspace routes (existing + new) — unchanged paths, now transparently tenant-scoped via tenant.context middleware.
  • /tenants/register, /tenants/lookup/{slug} — new self-service tenant signup, distinct from /auth/register (adds a customer to an existing tenant).
  • /platform/* — new platform-admin surface: tenant list/show/update/suspend/activate, membership plan CRUD, dashboard.
  • /integration/* — new API-credential-authenticated surface: customer CRUD + lookup, ticket CRUD + reply + status + attachments.
  • /api-credentials, /webhooks — new tenant-admin-facing management endpoints.

Existing endpoint paths and response shapes were preserved; no existing route was removed or renamed.

06 Authentication changes

  • POST /auth/register now requires a tenant slug (email is unique per tenant, not globally).
  • POST /auth/login, /auth/forgot-password, /auth/reset-password accept an optional tenant slug to disambiguate when the same email exists in more than one tenant — see Finding #5 for why this matters for password reset specifically.
  • A new, entirely separate authentication mechanism — X-Api-Key / X-Api-Secret headers — backs the Integration API, with no Sanctum session involved. Secrets are bcrypt-hashed (never recoverable); webhook secrets are encrypted (reversible, needed for HMAC signing) rather than hashed.

07 Authorization changes

  • spatie/laravel-permission's "teams" feature is now enabled (team_foreign_key = tenant_id): permissions stay global, but every tenant gets its own role rows.
  • A new, structurally separate Platform Admin population (tenant_id = NULL) governs the platform itself via platform.admin middleware, which checks the role directly — no tenant Administrator permission set can reach it.
  • Three new permission groups: api-credentials.*, webhooks.*, billing.*.
  • App\Models\Role now exists as a tenant-scoped subclass of spatie's own model — see Finding #2, the most severe authorization finding of this migration.

08 Scope implementation

Every API credential carries a scopes array, checked by RequireApiScope route middleware before any protected action executes:

customers.read   customers.create   customers.update
tickets.read     tickets.create     tickets.update
tickets.reply    tickets.status.update   tickets.attachments

A credential missing a required scope receives 403 regardless of whether its key/secret check succeeded. Verified in tests/Feature/Integration/IntegrationApiTest.php (a customers.read-only credential cannot create a customer).

09 Customer integration

A tenant's own backend/CRM/chat widget can identify its customers three ways, all scoped automatically to the credential's own tenant:

  • Internal id — customer_id, once already known from a prior integration call.
  • Email — customer_email / GET /integration/customers/lookup?email=....
  • External id — customer_external_id / ?external_id=..., the tenant's own foreign key into its system (e.g. wp-user-7842), stored as customers.external_id, unique per (tenant_id, external_id).

Ticket replies and attachment uploads made through the Integration API are attributed to the ticket's own customer, since no staff identity backs an API credential.

10 Subscription implementation

MembershipPlan (platform-level: Starter/Professional/Business/Enterprise, configurable limits, no hardcoded values in controllers) and Subscription (tenant-level, one per tenant) back a centralized PlanLimitService. Every resource-creating endpoint — tickets, customers, users, departments, API credentials, webhooks; both the regular and Integration API creation paths — calls assertCanCreate($tenant, $feature) before writing a row. Usage is computed live (a scoped COUNT, not a denormalized counter that can drift). Exceeding a limit returns 403 with {"errors": {"feature": "...", "limit": N}}. A tenant with no subscription is treated as unlimited (a data-integrity fallback — registration always creates one — not a billing decision). Verified end-to-end, not just wired, in tests/Feature/PlanLimitEnforcementTest.php.

11 Webhook implementation

  • Events: ticket.created, ticket.assigned, ticket.status_changed, ticket.resolved, ticket.closed, ticket.reopened, ticket.replied (both agent and customer replies). ticket.updated is reserved for a future general-attributes-changed event.
  • Delivery: one listener per ticket event dispatches a queued DeliverWebhookJob per subscribed, active webhook. Each attempt — success or failure — logs its own WebhookDelivery row, giving full retry history. Failures retry with backoff (10s/60s/5m/15m, up to 5 attempts) via Laravel's own queue retry, never a hand-rolled loop.
  • Signing: X-Webhook-Signature is an HMAC-SHA256 of the raw JSON body, keyed by the webhook's own secret, returned in plain text exactly once at creation.
  • SSRF protection: a new NotAPrivateUrl validation rule resolves the webhook URL's hostname and rejects loopback/private/link-local/reserved ranges at creation and update time, since the delivery job POSTs to tenant-supplied URLs unsupervised.

12 Security findings

Listed most severe first. Every finding below was verified by deliberately reverting its fix, confirming the associated test failed, then restoring the fix and confirming it passed again — not just inferred from code review.

Critical Route-model binding resolved before tenant context — application-wide cross-tenant data leak

Affects: every tenant-scoped route with a bound parameter (departments, customers, tickets, categories, priorities, statuses, SLA policies, routing rules, users, roles — and identically for the Integration API)
Root cause
Laravel's SubstituteBindings middleware — which runs the actual database query behind every {department}/{ticket}/{customer} route parameter — is part of the default api middleware group, which executes before any route-level middleware unless given explicit priority. ResolveTenantContext and ResolveIntegrationTenantContext were not in Laravel's default middleware-priority list (only Authenticate is), so tenant context was set after the bound model had already been fetched — unscoped — from the database.
Impact
On a genuinely cold request (the normal state of a fresh PHP-FPM worker — no prior request has left anything in the container), TenantScope is a deliberate no-op when no context is set, meaning the binding query ran completely unscoped. Any authenticated tenant user, or any valid API credential, could fetch, update, or delete any other tenant's row by id.
Why the existing test suite didn't catch it
Every isolation test used helpers (actingAsAdministrator(), testTenant()) that, as a side effect, pre-establish ambient tenant context before firing a request — which happens to coincidentally match what the middleware would have set anyway, masking the ordering bug entirely. It was found by deliberately writing a test that clears context first, simulating what a real fresh request actually looks like.
Fix
bootstrap/app.php: $middleware->prependToPriorityList(before: SubstituteBindings::class, prepend: ResolveTenantContext::class) (and identically for ResolveIntegrationTenantContext, RequirePlatformAdmin), forcing these to run first regardless of attachment point.
Regression coverage
tests/Feature/TenantIsolation/ColdRequestIsolationTest.php — two tests, deliberately clearing context before each request.

High spatie/laravel-permission's Role model had no tenant scoping on plain queries

Affects: GET/PUT/DELETE /roles, GET /roles/{id}
Root cause
Spatie's "teams" feature only scopes roles inside the package's own helper methods (findByName(), the roles() pivot relation) — never for a plain Role::all(), Role::find($id), or implicit route-model binding, since no global Eloquent scope is registered on the vendor model at all.
Impact
Any tenant admin calling GET /roles saw every other tenant's custom roles, including their full permission sets and user counts. The same gap allowed viewing, renaming, reassigning permissions on, or deleting another tenant's role by id.
Fix
Introduced App\Models\Role extends Spatie\Permission\Models\Role with the same BelongsToTenant trait every other tenant-owned model uses, and pointed config('permission.models.role') at it — plus updated every direct import of the vendor class to the new subclass, since a hardcoded use Spatie\Permission\Models\Role in any file would bypass the fix for that file's static calls.
Regression coverage
tests/Feature/TenantIsolation/CrossTenantAccessTest.php (role show/update/delete, and the role-listing-leak test).

Medium Editing a not-yet-overridden setting or notification template mutated the shared platform default

Affects: PUT /settings, PUT /notification-templates/{id}
Root cause
NotificationTemplate/SystemSetting use a platform-default-with-tenant-override pattern (TenantOverlayScope: a tenant sees the platform default for any key it hasn't customized). The original update() code looked the row up by key alone; for a key no tenant had overridden yet, that lookup resolved to the shared platform-default row, and the update mutated it directly — silently changing what every other tenant also saw.
Fix
Copy-on-write: SystemSettingController::update() now includes tenant_id in the updateOrCreate() match array, so a first edit misses the shared row and inserts the tenant's own instead. NotificationTemplateController::update() checks whether the resolved row's tenant_id already matches the caller's tenant and forks a new row if not.
A second bug this uncovered
Both tables' key column still had a global unique constraint from before multi-tenancy — meaning the copy-on-write insert could never actually have succeeded; it would collide with the platform default's own row. This went unnoticed because the pre-fix code never attempted an insert at all. Fixed via migration ...000012, moving both to a composite (tenant_id, key) constraint.
Regression coverage
tests/Feature/TenantIsolation/TenantOverrideWriteTest.php.

Systemic ~17 Form Request classes had tenant-unscoped unique:/exists: validation rules

Affects: tickets, departments, users, roles, categories, priorities, statuses, SLA policies, assignment
Root cause
Every validation class predating multi-tenancy that validated a field against a now-tenant-scoped table still did so with a bare unique:table,column or exists:table,column rule, which runs as a raw query bypassing Eloquent's global scopes entirely.
Impact — two distinct failure modes
False rejection: creating a department/role/status/priority with a code, name, or slug that any other tenant already used (perfectly legitimate — these are unique per tenant, not globally) was rejected with a 422.
Cross-tenant linkage: staff could set a ticket's category_id/priority_id/customer_id, an SLA policy's department_id, an assignment's assignee_id, or a new staff user's department_ids to a row belonging to a different tenant, since the existence check never verified tenant ownership.
Fix
Every affected rule converted to Rule::unique(...)->where('tenant_id', $tenantId) / Rule::exists(...)->where('tenant_id', $tenantId), scoped to the acting user's (or API credential's) own tenant. Globally-correct rules (platform-level tables: tenants, membership plans, permissions) were deliberately left unscoped.
Regression coverage
tests/Feature/TenantIsolation/CrossTenantValidationTest.php — one test per cross-tenant-reference rejection, paired with a same-value-different-tenant success case for each, to guard against the fix over-correcting into false rejections again.

Medium ReportController::slaCompliance() aggregated SLA data across all tenants

Affects: GET /reports/sla-compliance
Root cause
Used DB::table('ticket_slas') directly instead of the TicketSla Eloquent model — a raw query builder call bypasses Eloquent global scopes entirely, so TenantScope never applied.
Impact
A tenant's SLA compliance report silently included every other tenant's breach counts and totals.
Fix
Switched to TicketSla::count() / TicketSla::where(...)->count(), correctly scoped.
Regression coverage
tests/Feature/TenantIsolation/CrossTenantAccessTest.php (SLA compliance report test).

Medium Password reset could resolve the wrong tenant's account when an email was shared

Affects: POST /auth/forgot-password, POST /auth/reset-password
Root cause
Email is unique per tenant, not globally, by design — the same address can be a different account in each of several tenants. Laravel's password broker resolves a reset request by email alone; with no disambiguator, the account that happens to be returned first by the lookup query (not necessarily the one the caller meant) receives the reset.
Fix
Added an optional tenant slug to both endpoints, passed through as an extra credential key — EloquentUserProvider::retrieveByCredentials() adds every non-password credential key as an additional WHERE clause, so this resolves the lookup to the exact intended tenant's account instead of leaving it ambiguous.
Regression coverage
tests/Feature/TenantIsolation/PasswordResetIsolationTest.php — deliberately targets the higher-id (non-default-match) account to prove the disambiguator is actually used, not just coincidentally correct.

Hardening SSRF exposure via tenant-supplied webhook URLs

Affects: POST/PUT /webhooks
Context
Not a regression — a risk inherent to the webhook feature being built, addressed proactively rather than discovered after the fact.
Fix
App\Rules\NotAPrivateUrl resolves the submitted URL's hostname and rejects it if any resolved address falls in a loopback, private, link-local, or reserved range, or if the hostname doesn't resolve at all.
Coverage
tests/Feature/WebhookManagementTest.php (127.0.0.1, localhost, 10.x, 192.168.x all rejected).

15 Breaking changes

  • POST /auth/register now requires a tenant field — a pre-existing client calling this endpoint without one will receive a 422 where it previously succeeded.
  • Email uniqueness changed from global to per-tenant across users, customers, and related lookups — a client that relied on email being a stable global identifier (e.g. for caching or deduplication across the whole platform) must now pair it with tenant context.
  • Two pre-existing tests (AuthenticationTest::it_registers_a_new_customer_and_issues_a_token, it_rejects_registration_with_a_duplicate_email) were updated to send the new required tenant field and expect the new per-tenant validation error shape — an intentional contract change, not a regression.
  • No existing endpoint path, response envelope shape, or HTTP status code convention was changed.

16 Migration risks

  • Backfill migration is a one-way door. backfill_default_tenant_and_tighten_constraints assigns every pre-existing row to a single "Default Organization" tenant, which is correct only because this installation had exactly one tenant's worth of data before this migration. Running it against a database that already mixed multiple unrelated organizations' data would silently merge them under one tenant — the migration does not attempt to detect or guard against that case.
  • MODIFY COLUMN ... NOT NULL is MySQL-only. The same migration skips tightening tenant_id to NOT NULL on SQLite (would require doctrine/dbal); correctness there relies on the application layer (BelongsToTenant's creating-hook) always populating it, which the test suite exercises but a direct INSERT bypassing Eloquent would not.
  • Queue driver assumption. Webhook delivery and notification listeners are ShouldQueue; under a real async queue (the intended deployment), a failing webhook endpoint never affects the request that triggered it. Under QUEUE_CONNECTION=sync (as this test suite runs), a queued job's exception propagates synchronously all the way back to the triggering HTTP response — not a new risk introduced by this migration (the pre-existing notification listeners already had the same characteristic), but worth confirming the deployment target never runs the sync driver in production.

17 Remaining work

Updated 2026-10-03 — the four items below were closed out after the first pass of this report; the last two are still open.

  • Plan-configurable, tenant/credential-aware API rate limiting. A new integration named rate limiter (AppServiceProvider) reads each plan's api_requests_per_day and applies Limit::perDay($limit)->by($credential->id) to every /integration/* request; a 429 carries {limit, period, retry_after_seconds} plus standard Retry-After/X-RateLimit-* headers. Required its own middleware-priority fix (ResolveIntegrationTenantContext before ThrottleRequests, not just before SubstituteBindings) — same bug class as finding #1, caught by reasoning through SortedMiddleware::sort() before it shipped rather than by a failing test. Tests: IntegrationRateLimitTest.php.
  • Webhook "test delivery" and secret-rotation endpoints. POST /webhooks/{webhook}/test sends a synthetic webhook.test event synchronously (no queue, no retry) via a new WebhookDispatcher::test(), logged as an ordinary WebhookDelivery row; POST /webhooks/{webhook}/rotate-secret issues a new secret without deleting/recreating the webhook, mirroring ApiCredentialController::rotate(). Tests added to WebhookManagementTest.php.
  • Tenant-specific email configuration. Reuses the existing SystemSetting platform-default/tenant-override mechanism (no schema change) for email.sender_name, email.reply_to (falling back to support_email) and email.branding_signature; TicketEventNotification::applyTenantEmailConfig() applies them to the outgoing MailMessage's From name, Reply-To and salutation. Tests added to NotificationTest.php.
  • Audit logging coverage expanded to match the spec's action list: auth.login, ticket.assigned, customer.created, user.created, user.role_changed, api_credential.created/secret_rotated/revoked, webhook.created/updated/secret_rotated/deleted (in addition to the ticket-creation/status-change and platform-tenant actions already covered). auth.login needed an explicit TenantContext::runAs() since /auth/login runs with no tenant.context middleware. Tests: AuditLogCoverageTest.php.
  • Billing changed: there is still no platform-admin endpoint to alter an existing tenant's subscription/plan after registration, so this one action from the audit list has nothing to log yet — out of scope for the audit-logging fix itself, which only wires up actions that already have an endpoint.
  • A platform-level endpoint to edit the shared default notification templates/system settings (the copy-on-write tenant-override path is complete; nothing yet lets a platform admin edit the defaults themselves through the API, only via seeders).
  • Observability: no centralized logging yet specifically around tenant-resolution failures, scope failures, or webhook delivery failures beyond what's captured in webhook_deliveries.
