Executive Summary

This report covers a systematic QA pass across the SupportHub helpdesk application — full backend code inspection, full frontend code inspection, live API testing against a running Docker environment seeded with representative demo data across all five roles, database-level constraint verification, the existing automated test suite — followed by a fix-and-retest pass: every issue below that could be fixed with an objectively-correct code change was fixed, covered by a new automated regression test where the existing suite had a gap, and re-verified live against a freshly-rebuilt environment. 33 issues were identified in total; 28 are now fixed and re-verified, and 5 are explicitly flagged for a product/team decision rather than fixed unilaterally (see each one's "why this wasn't changed" note). The one Critical-severity issue found — a cross-ticket message disclosure (IDOR) — is fixed; the regression test that proved it (previously red, by design) is now green.

Scope & Methodology

Per the instruction to test actual implemented functionality rather than assume expected behavior exists, the codebase was inspected first. The following sections of a generic SaaS-helpdesk test brief do not apply to this application and are marked N/A rather than fabricated:

Multi-tenancyNot implemented. SupportHub is a single-organization helpdesk — confirmed by grep (zero matches for "tenant" anywhere in app/). "Tenant isolation" testing was performed as Customer Data Isolation instead (the real boundary that exists in this app) — see that section.
API credentials / API keysNot implemented. No ApiCredential model, controller, or routes exist.
WebhooksNot implemented. No Webhook model, controller, or routes exist. (One seeded demo ticket's subject mentions "webhook" as sample support-request text only — not a real feature.)
Guest ticket accessNot implemented. All ticket creation requires an authenticated account (customer self-service registration, or staff creating on a customer's behalf) — there is no anonymous/guest/secure-token ticket flow.

What was tested:

  • Backend: every one of the 85 /api/v1/* routes inspected (controller, FormRequest validation rules, Policy authorization, API Resource shape); live HTTP testing against a running Docker stack (Laravel 13 + MySQL 8 + Redis, seeded with DemoTicketSeeder) authenticated as all 5 roles across 9 demo accounts.
  • Frontend: every screen/page, every API call made from the client, every create/edit form, forms validation, loading/error/empty states, and permission-gating reviewed via full source inspection; the Vite dev server, TypeScript build, and linter were run to confirm a clean baseline.
  • Database: foreign key constraints, cascade behavior, soft-delete configuration, and unique constraints inspected directly against the live MySQL schema.
  • Automated tests: the existing Pest suite (84 tests) was run as a baseline (100% passing before this QA pass), then one new regression test was added proving the Critical IDOR finding — it fails by design until the underlying code is fixed, per the instruction not to weaken tests or silently patch product code during QA.

Known limitation: no browser-automation tooling was available in this environment, so interactive/visual UI testing (clicking through screens, responsive-breakpoint screenshots) was not performed live. Frontend coverage in this report comes from exhaustive source-code inspection (every page, component, API call, and form was read in full) plus confirming the app actually builds and serves without error — not from driving a real browser. This is stated explicitly rather than claiming UI testing that didn't happen.

Steps to Reproduce

  1. From the repo root, run: docker build --target production -f docker/php/Dockerfile -t test .
  2. Observe the composer install --no-dev step fail during its post-autoload-dump package:discover hook.

Expected Result

A successful production image build, matching what docker-compose.yml's production target and any real deployment would rely on.

Actual Result (before fix)

Every attempt (reproduced identically 3 times in this session before being fixed) fails with: "In scribe.php line 117: Class \"Knuckles\\Scribe\\Config\\AuthIn\" not found" — composer install --no-dev correctly removes the dev-only knuckleswtf/scribe package, but Laravel's LoadConfiguration bootstrapper unconditionally loads every file in config/ (including config/scribe.php, which references Scribe's classes at the top level) on every artisan command — including package:discover, which runs as a post-autoload-dump hook inside the same composer install that just removed the package.

Root Cause

config/scribe.php (Scribe's standard published config) hard-imports and references Knuckles\Scribe\Config\AuthIn/Defaults and Knuckles\Scribe\Extracting\Strategies at the top level, with no guard for the package being absent — fine in any environment where scribe is installed (local dev, CI), fatal in any --no-dev build.

Impact

The production Docker target — the one any real deployment of this app would use — has apparently never successfully built. This was invisible during normal development because nobody builds that target locally; it was only discovered because this QA pass needed to rebuild the demo container to verify the application-level fixes.

Fix Applied

Added `if (! class_exists(AuthIn::class)) { return []; }` immediately after config/scribe.php's use statements. Nothing reads config('scribe.*') outside Scribe's own artisan commands, so short-circuiting to an empty config when the package isn't installed is safe and has zero effect in any environment where Scribe is actually present (local dev, CI, or a future doc-generation step).

✓ What changed

Guarded config/scribe.php to return an empty config array when the knuckleswtf/scribe package is not installed, instead of crashing Laravel's unconditional config-loading bootstrapper.

How it was verified after the fix

docker build --target production now completes successfully end-to-end (verified in this session); local Pest suite (94/94) unaffected since the package is present in dev.
